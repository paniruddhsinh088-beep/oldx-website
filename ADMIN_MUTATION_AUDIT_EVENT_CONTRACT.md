# Admin Mutation Audit Event Contract

**Status:** implementation contract for review; no audit store or cloud runtime is deployed.  
**Scope:** future staging-only Admin mutation adapter.  
**Production:** explicitly excluded.

## Required atomic behavior

Every privileged mutation must be committed together with exactly one append-only audit event in the same trusted Firestore transaction or atomic batch. If the business write or audit write fails, the entire operation must fail. Never write the business change first and attempt a separate audit write afterward.

## Server-derived event envelope

The trusted adapter, not the browser, constructs the audit envelope:

| Field | Requirement |
|---|---|
| `eventId` | Server-generated unique identifier |
| `occurredAt` | Firestore server timestamp, never client time |
| `actorUid` | Verified Firebase ID-token UID |
| `actorRole` | Server-resolved active role at request time |
| `operation` | Exact server allowlisted operation name |
| `requestId` | Handler-generated or validated bounded request ID |
| `targetType` | Server-validated domain type |
| `targetId` | Server-validated target identifier; avoid unnecessary personal data |
| `outcome` | Committed success only; failed attempts belong in a separate security log if explicitly designed |
| `reasonCode` | Optional bounded enumerated reason, not unrestricted client text |

Do not accept actor UID, actor role, event timestamp, event ID, outcome, or audit document path from request body. The HTTP handler's server-derived context fields are authoritative; client body values are merely untrusted domain input.

## Data minimization

- Do not record passwords, ID tokens, refresh tokens, session cookies, secrets, full request headers, payment details, or full user documents.
- Avoid copying arbitrary request bodies into audit records.
- Store only the minimum target identifiers and approved change summary needed for accountability.
- Any free-text reason must be bounded, sanitized, and reviewed for personal or sensitive information.
- Audit reads must be separately authorized, paginated, no-store, and themselves logged where appropriate.

## Immutability and access

- Audit events are append-only.
- Admin UI operations must not grant permission to update or delete audit events.
- No Admin may grant/revoke/promote Admin identities or edit the owner-controlled role registry.
- Retention, legal hold, export, and deletion policy require owner/legal review before implementation.
- A request ID is for correlation, not a substitute for an idempotency key. Any retry-safe mutation must define a separate server-validated idempotency strategy.

## Required tests before any runtime enablement

1. Business write and audit event both commit on success.
2. Audit write failure rolls back the business mutation.
3. Business write failure creates no success audit event.
4. Client-supplied actor fields and timestamps are ignored.
5. Event timestamp is generated by Firestore server time.
6. Duplicate/replayed requests follow an explicit idempotency policy.
7. Audit event cannot be updated/deleted by Admin-facing operations.
8. Audit payload excludes credentials and unapproved personal data.
9. Revoked Admin is denied before the transaction begins.
10. Synthetic Emulator tests prove transaction semantics before staging rollout.

## Explicit non-authorization

This contract does not authorize Firestore Rules changes, indexes, IAM, service identities, secrets, billing, data migrations, staging scans, backend provisioning, or deployment. The current handler only injects a `commitMutation` dependency; it does not itself implement a transaction or persist an audit event.

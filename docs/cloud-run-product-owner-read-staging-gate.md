## Runtime and identity

- The existing container entrypoint binds to `0.0.0.0:$PORT` in its default mode, rejects invalid ports and drains on SIGTERM. The emulator SDK bootstrap remains restricted to the demo project and fixed loopback Auth/Firestore ports. The separate staging initializer is disabled by default. Do not reuse emulator flags or the Vercel preview configuration as Cloud Run activation controls. [Cloud Run container contract](https://docs.cloud.google.com/run/docs/container-contract)
- Use `GET /healthz` as a process startup/liveness probe. A 200 confirms HTTP process health even when the owner route returns 503. Prove backend readiness separately with an authenticated synthetic owner request and negative tests. Keep readiness probes free of privileged data and quota writes. [Cloud Run health checks](https://docs.cloud.google.com/run/docs/configuring/healthchecks)
- For future staging wiring, pin the Admin project to `oldx-staging` (project number `38472235077` to be confirmed during approved preflight), select the reviewed database, reject emulator settings and credential-file overrides, and fail closed on invalid scope, configuration or missing enforcement. Use Cloud Run ADC with a dedicated staging service account. No downloaded key, Secret Manager access or application secret is required by this runtime design. Separate runtime, deployer and invoker identities. Limit deployer access to the approved service/image and service-account attachment (`iam.serviceAccounts.actAs` on that identity). [Cloud Run service identity](https://docs.cloud.google.com/run/docs/securing/service-identity)
- Candidate custom runtime grants to verify with the pinned SDK: `firebaseauth.users.get` on the staging project for revocation and disabled-account lookup, plus `datastore.databases.get` for transactions and `datastore.entities.get/create/update` for Firestore point reads and rate-counter upserts. Validate the actual operations and denied operations before accepting the grants. Exclude entity list/delete, Auth mutation, Rules, Storage, IAM administration and production access. Scope Firestore IAM to the approved database where supported. Firestore IAM grants are not per collection or document. If database scope is too broad for this principal, stop for an isolation decision. [Firebase session verification](https://firebase.google.com/docs/auth/admin/manage-sessions), [Auth lookup permission](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/accounts/lookup), [Firestore IAM](https://docs.cloud.google.com/firestore/native/docs/security/iam)
- Owner reads consult `marketplaceActors_v1` and `marketplacePrivate_v1`, plus `marketplaceReceipts_v1` and `marketplaceAudit_v1` for recovery lookups. Allowed quota consumption reads and upserts two documents in `marketplaceRateLimits_v1`. Read-only Product semantics therefore still require writes for abuse control. Preserve the existing deny-all client Rules. The Admin SDK relies on IAM and server-side actor/ownership checks. [Firestore IAM](https://docs.cloud.google.com/firestore/native/docs/security/iam)

## Staging routing and authentication

1. Start with a private Cloud Run service and a named staging tester with service-level `roles/run.invoker`. The Google-signed service audience token goes in `X-Serverless-Authorization`. The distinct Firebase staging user token goes in `Authorization`. The application derives identity from the verified Firebase token and checks revocation, actor eligibility and ownership. The two credentials are independent. [Cloud Run service-to-service authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)
2. Keep Pages static and its existing API fallback until direct private acceptance passes. For later browser acceptance, propose one staging-only Pages Function for exact `POST /api/staging/marketplace/owner`, with a fixed approved HTTPS service origin and an exact route allowlist. Strip client invoker/identity headers, enforce the 32 KiB request limit, forward only the Firebase bearer and JSON, add a server-obtained Google invoker token, reject upstream redirects and use private no-store responses. Return a generic error on failure without falling back to HTML. Apply no token or private DTO logging at either hop. No route or origin changes are needed for production or Capacitor in this slice. [Pages Functions routing](https://developers.cloudflare.com/pages/functions/routing/)
3. The Pages Function still needs an independently reviewed, tested keyless Google token source. Do not assume Pages provides a federatable identity. Any external identity provider or Workload Identity Federation trust requires separate approval. Keep Cloud Run private and leave Pages routing off until that dependency is established. [Cloud Run external authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)

## Final offline preflight

### Pages workload identity verdict

Google supports a keyless external call when an independently trusted provider issues a renewable, signed **workload** assertion. The flow is provider assertion → Google STS → IAM Credentials `generateIdToken` for the Cloud Run service audience → `X-Serverless-Authorization`. Restrict the provider mapping and conditions to the exact staging workload and audience, and give the federated principal only `iam.serviceAccounts.getOpenIdToken` on an invoker-only account if the approved exchange supports that grant. The Firebase user bearer remains separate. [Google external invocation](https://docs.cloud.google.com/run/docs/authenticating/service-to-service) · [Workload assertion requirements](https://docs.cloud.google.com/iam/docs/use-workload-identity-federation-to-let-customers-access-their-cloud-resources) · [Token minting permissions](https://docs.cloud.google.com/iam/docs/service-account-permissions)

No documented native Pages Function workload assertion or tested trust binding was found. A Pages Service binding reaches a Worker and does not establish a Google principal. The Access plugin validates incoming Access assertions and does not supply a Pages workload assertion. GitHub OIDC identifies a workflow job. It does not identify the deployed Pages Function at request time. Service account keys and shared service tokens do not meet this keyless gate. [Pages bindings](https://developers.cloudflare.com/pages/functions/bindings/) · [Access plugin](https://developers.cloudflare.com/pages/functions/plugins/cloudflare-access/) · [GitHub workflow federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines)

**Decision:** Keep Pages static for the first private staging test and use a named Google tester plus a separate synthetic Firebase identity. If browser-only staff acceptance is later needed, evaluate direct Cloud Run IAP as a distinct, separately approved user-access design. IAP grants invocation to its service agent and gates staff access. It does not give Pages a workload identity. Public invocation is outside this plan. [Developer authentication](https://docs.cloud.google.com/run/docs/authenticating/developers) · [Direct IAP](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run)

### Runtime npm dependency review

Audited the unchanged image manifests from `fd9d263a80af3d27041e6cd14a5161e4b1016a49`. The Dockerfile installs the lockfile with `npm ci --omit=dev --ignore-scripts`. `npm audit --omit=dev --json` returned **6 moderate, 0 low, 0 high, 0 critical**. The full lockfile audit returned **11 moderate** with the same other counts. Five additional records are confined to development tooling: `firebase-tools`, `exegesis`, `archiver`, `archiver-utils`, and `zip-stream`.

- Production path: `firebase-admin@14.5.0 → @google-cloud/firestore@9.4.0 → @google-cloud/firestore-api@0.2.0 → google-gax@5.0.8 → rimraf@5.0.10 → glob@10.5.0 → minimatch@9.0.9`. The same vulnerable rimraf is reached via `google-gax@5.0.8 → google-auth-library@10.5.0 → gcp-metadata@8.1.4 → gaxios@7.1.3 → rimraf@5.0.10`. The six npm records include four propagated dependency findings and two primary advisories.
- **Glob** can continue filesystem traversal after cancellation. **Minimatch** can amplify attacker-controlled patterns during preprocessing at optimization level 2 or higher, consuming CPU and memory. Both are availability issues. The current Product owner route accepts bounded JSON and sends validated IDs into fixed Firestore document lookups. Review found no request-derived glob pattern, directory root or filesystem traversal path in that route. The production packages are present and the assessment is limited to this code path. Live ADC and other entrypoints were outside the reachability test. [Glob advisory](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4) · [Minimatch advisory](https://github.com/advisories/GHSA-g3hv-75wg-m249)
- No runtime manifest or lockfile change was made. The registry's latest Firebase Admin and Firestore versions match the lockfile. Firestore requires `firestore-api ^0.2.0`; that release requires `google-gax ^5.0.0` and the newest 5.x is 5.0.8. Both affected consumers require `rimraf ^5.0.1`, while the patched downstream chain first appears in rimraf 6.1.4. Patched glob 14.0.2 and minimatch 11.0.1 also exceed the affected parents' ranges. Forcing those major changes or upgrading the pre-1.0 Firestore API outside its declared range is outside this review. Recheck when the SDK publishes a compatible update or when a route introduces a filesystem pattern or traversal input.
- The actual Ubuntu Docker run for the unchanged image inputs passed packaging (1 test), startup/health, disabled owner, invalid PORT, shutdown and two isolated Auth/Firestore Emulator tests.
